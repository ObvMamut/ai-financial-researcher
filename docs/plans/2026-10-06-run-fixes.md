   way it is spelled here". But `Attribution.Cells` / `cellCounts`
   (`internal/scoreboard/attribution.go:327`, `postmortem.go:147`) key on the bare bucket
   (`sell/wide-stop`), so `ParsePostMortem` rejects every correctly spelled lesson as "names no
   cell". The rejected cells exist with n = 5–9. The loop the post-mortem closes has been open.
2. **AlphaVantage NEWS_SENTIMENT is now a premium endpoint.** All 12 per-ticker calls came back
   "This is a premium endpoint" (12 of 18 `data_errors`). `rememberDailyQuota`
   (`internal/marketdata/alphavantage.go:388`) only recognises the daily-limit message, so the
   run kept spending AV calls (25/day budget, shared with the earnings calendar) and logged each
   as a fetch failure. EARNINGS_CALENDAR still works (8 verified dates this run). Alpaca and Yahoo
   news still cover US names.
3. **`merit_veto` ships pairs the risk gate calls one bet.** ENI.MI and TTE.PA correlate 0.81
   (> `max_pair_corr` 0.75). `gateBook` says "swap the weaker one", but under `merit_veto` nothing
   swaps: `pickBook` (`internal/orchestrator/selection.go:211`) enforces `max_per_sector` and
   not the pair limit. The next eligible merit name was NKE SELL (BBVA.MC was risk-gated).
4. **Five of eight warnings are noise.** `applyEntryPolicy` (`riskgate.go:371`) reports
   "stop 0.00 widened to …" for every merit idea, because Go builds them with no stop and then
   *places* the catastrophe floor. That is placement, not a correction.

Not changed, by ruling: the 3-name news gap (BBVA.MC, HDFCBANK.NS, PHIA.AS) that made the run
`degraded` is real. Alpaca and Yahoo were asked and found nothing relevant, so the flag is

## Rulings

- **R1:** a lesson's cell matches when it equals either the rendered label (`<family> <key>`, the
  exact prefix `Lines` uses: `setup`, `coverage`, `agreement`, `sector`, `entry`) or the bare
  key, case-insensitive. Labels come from one helper that `Lines`, `Cells` and `cellCounts` all
  use, so prefixes cannot drift apart again.
- **R2:** an AV message containing "premium endpoint" disables NEWS_SENTIMENT for the rest of
  the process. The first refusal is returned as `ErrNotApplicable`, with one diagnostic naming
  the cause, and later tickers are skipped without a request. Not persisted: one call per run
  re-checks, in case the key is upgraded. The calendar is unaffected.
- **R3:** `pickBook` skips a candidate whose daily-return correlation with an already-picked
  *same-direction* name exceeds `MaxPairCorr`, using the same `quant.Correlation` on the same
  verified series `gateBook` uses. Merit order refills the slot, as the sector cap does. The
  selection row records `excluded: "correlated"` and names the partner. Setting
  `max_pair_corr >= 1` disables it. `gateBook` keeps its check, so the `chief` policy is
  unchanged. This is a risk control the config already declares, applied on the one path that
  ignored it. It is not an edge claim.
- **R4:** `applyEntryPolicy` places the floor silently when `idea.Stop <= 0`, and still warns
  when a given stop is widened.
